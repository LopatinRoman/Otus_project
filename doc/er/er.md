# ER-диаграмма

## Назначение
ER-диаграмма описывает модель данных MVP **HR Onboarding Hub (1С)**: создание заявки онбординга HR, формирование этапов по выбранному пакету доступов и отслеживание выполнения этапов (в т.ч. через интеграцию с RabbitMQ).

---

## Сущности и их смысл

### 1) `otus_Сотрудники` (справочник)
Хранит сотрудников, для которых создаются заявки онбординга.

**Ключ:** ссылка справочника.  
**Основные реквизиты:** ФИО (Наименование), Подразделение, Должность.

---

### 2) `otus_ПакетыДоступов` (справочник)
Хранит типовые наборы доступов/действий, которые нужно выполнить при онбординге.

**Ключ:** ссылка справочника.  
**Основные реквизиты:** Код, Наименование.

---

### 3) `otus_ПакетыДоступов.ТЧ Этапы` (табличная часть)
Состав пакета доступов — перечень этапов, которые необходимо выполнить, и их параметры.

**Ключ строки:** (ПакетДоступов + НомерСтроки).  
**Основные колонки:** ТипЭтапа, Порядок, SLAЧасов.

---

### 4) `otus_ТипыЭтапов` (справочник)
Классификатор этапов онбординга. Используется:
- при наполнении пакетов доступов (в табличной части),
- при создании записей в регистре этапов,
- для определения типа команды интеграции (например, какой `message_type` отправлять во внешний контур).

**Ключ:** ссылка справочника.  
**Основные реквизиты:** Наименование, СрокSLAЧасов, ТипКомандыRMQ.

---

### 5) `otus_ЗаявкаОнбординг` (документ)
Заявка HR на онбординг конкретного сотрудника. Определяет параметры запуска процесса:
- кто (сотрудник),
- когда выходит,
- какой пакет работ/доступов применить,
- нужно ли оборудование,
- текущий статус заявки.

**Ключ:** ссылка документа.  
**Основные реквизиты:** Сотрудник, ДатаВыхода, ПакетДоступов, НужноОборудование, Статус.

---

### 6) `Otus_ЭтапыОнбординга` (регистр сведений, непериодический)
Основной “движок” процесса: хранит этапы по каждой заявке и их текущее состояние.

**Ключ (измерения):**
- Заявка (ссылка на документ),
- ТипЭтапа (ссылка на справочник типов этапов),
- НомерЭтапа (порядковый номер этапа в рамках заявки).

**Основные поля состояния:**
- СтатусЭтапа,
- Дедлайн,
- ДатаФакта,
- Просрочен.

**Поля интеграции (трассировка):**
- CorrelationId (сквозной идентификатор этапа),
- LastRequestId (идентификатор последней попытки отправки/запроса).

---

## Связи между сущностями

### `otus_Сотрудники` → `otus_ЗаявкаОнбординг`
**Тип связи:** 1 → N  
Один сотрудник может иметь множество заявок онбординга.  
В документе хранится ссылка `Сотрудник`.

---

### `otus_ПакетыДоступов` → `otus_ЗаявкаОнбординг`
**Тип связи:** 1 → N  
Один пакет доступов может быть выбран во множестве заявок.  
В документе хранится ссылка `ПакетДоступов`.

---

### `otus_ПакетыДоступов` → `ТЧ Этапы`
**Тип связи:** 1 → N  
У одного пакета — множество строк табличной части, определяющих состав пакета.

---

### `otus_ТипыЭтапов` → `ТЧ Этапы`
**Тип связи:** 1 → N  
Каждая строка состава пакета ссылается на один тип этапа.

---

### `otus_ЗаявкаОнбординг` → `Otus_ЭтапыОнбординга`
**Тип связи:** 1 → N  
Одна заявка порождает множество этапов (записей регистра).  
Связь осуществляется по измерению `Заявка`.

---

### `otus_ТипыЭтапов` → `Otus_ЭтапыОнбординга`
**Тип связи:** 1 → N  
Каждый этап в регистре ссылается на тип этапа (измерение `ТипЭтапа`).

---

## Логика формирования этапов (в контексте ER)
1) HR создаёт `otus_ЗаявкаОнбординг` и выбирает `ПакетДоступов`.
2) Система читает состав пакета (`ТЧ Этапы`) и на его основе создаёт записи в `Otus_ЭтапыОнбординга`.
3) Для каждой записи этапа устанавливаются дедлайны (SLA) и значения для трассировки интеграции (`CorrelationId`, `LastRequestId`).

---

## Что сознательно не отражено в MVP ER
Сокращённая ER-диаграмма **не включает**:
- служебные регистры/хранилища сообщений интеграции (если есть),
- справочник `otus_Оборудование` и его статусный учёт,
- перечисления статусов как отдельные сущности (в диаграмме они сведены к реквизитам `Статус/СтатусЭтапа`).
